# OPC API 与数据契约

## 1. API 分类与所有权

API 至少分为 C 端公开 API、B 端管理 API、内部服务 API、运维管理端点。每个接口必须有所有模块、调用方、认证方式、权限、稳定性级别和数据分类。不同类别使用明确路径或网关策略隔离，禁止仅靠前端隐藏。

## 2. 接口设计

- 使用 HTTPS；请求和响应采用稳定、文档化的 JSON 契约。
- 输入校验在边界完成；字段长度、格式、枚举、时区、金额精度和分页上限必须明确。
- 时间使用 ISO 8601 并明确时区；服务端存储优先 UTC，展示层转换。
- 金额使用定点小数或最小货币单位，不使用浮点计算。
- 列表接口必须分页并限制最大页大小；排序和过滤字段使用白名单。
- 写接口定义幂等策略。创建订单、任务、导入等可重试场景应支持幂等键或业务唯一约束。
- 错误响应包含稳定错误码、用户可理解信息和追踪标识，不暴露内部堆栈。

## 3. 版本与兼容性

- 默认采用向后兼容演进：新增可选字段、保持旧字段语义、消费者容忍未知字段。
- 删除/改名字段、改变类型或语义、收紧原有合法输入均属于破坏性变更。
- 破坏性变更必须版本化，提供迁移窗口、调用方清单、弃用监控和下线日期。
- API 文档与实现同一 PR 更新；契约测试阻止文档和运行行为漂移。
- 前端不得依赖未文档化字段、数据库 ID 规律或错误文本做业务判断。

## 4. 数据所有权

- 每个核心数据集必须有唯一负责模块；其他模块通过服务契约访问，不直接修改其表。
- 数据库约束负责最终完整性，应用校验负责用户反馈；唯一性、非空和引用关系不能只靠前端。
- 表和字段命名表达业务含义；审计字段、逻辑删除和状态字段采用统一约定。
- 关键状态变化保留操作者、时间、来源、前后值或领域事件，审计记录不可被普通业务用户修改。

## 5. 数据库变更

当前仓库尚无迁移框架。在引入 Flyway/Liquibase 前，SQL 脚本必须版本化、顺序明确、经双人审查并记录执行结果。正式环境不得手工执行未纳管 SQL。

- 采用 expand/migrate/contract：先增加兼容结构，再迁移/双写或回填，最后在独立发布清理旧结构。
- 大表操作必须评估锁、磁盘、复制延迟和执行时间，并提供分批、暂停与恢复方法。
- 回填脚本必须幂等、可观测、限速并校验行数；失败后可从检查点继续。
- 发布前验证备份可恢复；“已备份”但未演练恢复不视为回滚方案。
- 数据清理和不可逆迁移要求业务、数据库和安全负责人批准。

## 6. 隐私与数据生命周期

数据按公开、内部、机密、敏感个人信息分类。收集前明确目的和最小字段；定义保留期限、归档、删除、导出和主体请求处理流程。

- 非生产环境禁止复制未脱敏生产数据。
- 日志、指标、追踪、备份和导出同样受数据分类约束。
- 文件上传必须校验类型、大小、内容和存储路径，使用随机对象名并隔离执行权限。
- 导出文件应有权限、有效期、水印/审计（适用时）和安全销毁策略。

## 7. 缓存与一致性

MySQL 是业务事实来源时，Redis 不得成为唯一持久副本。每个缓存定义键格式、所有者、TTL、一致性模型和失效方法。写后删缓存或事件失效必须考虑并发窗口；关键强一致流程直接读取事实来源或使用可证明的同步机制。
