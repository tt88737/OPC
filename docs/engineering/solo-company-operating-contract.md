# OPC 一人公司运营与工程契约

## 1. 目的与适用范围

本契约定义个人负责人使用 Codex 建设、运营和交付 OPC 时的最小治理模型。它适用于产品决策、研发、发布、客户支持、数据处理和事故响应。目标不是模拟大团队流程，而是在单人资源约束下保留必要的安全边界、可追溯性和恢复能力。

本契约与其他工程契约冲突时，安全边界、数据保护、自动化门禁和生产变更规则优先。任何“只有我一个人”的理由都不能降低这些要求。

## 2. 角色与决策权

同一个人可以承担多个角色，但每次任务必须在记录中标明当前角色，避免把“实现完成”误当成“风险已接受”。

| 角色 | 最终责任 | Codex 可协助 | 不得委托给 Codex |
| --- | --- | --- | --- |
| 产品负责人 | 用户价值、范围、优先级、验收 | 整理需求、拆分任务、提出方案 | 代表用户改变目标或默认扩大范围 |
| 技术负责人 | 架构、接口、数据、兼容性 | 读码、设计、实现、测试、证据汇总 | 无证据批准高风险设计 |
| 发布负责人 | 发布窗口、变更批准、回滚 | 生成清单、执行已授权命令、观察指标 | 自行决定生产发布或跳过门禁 |
| 数据/安全负责人 | 秘密、权限、个人数据、备份恢复 | 威胁建模、静态检查、验证脚本 | 读取、输出或保存真实秘密；执行破坏性数据操作 |
| 客户支持负责人 | 反馈分级、沟通、承诺 | 归纳反馈、生成回复草稿、建立复现步骤 | 未经确认向客户承诺时限、赔偿或行为变化 |

高风险任务至少保留“设计者”和“批准者”两条记录。单人场景下批准者仍由负责人明确执行，可以是同一自然人，但不能由测试通过或 Codex 自行推断替代。

## 3. 工作边界

- Codex 可以在授权范围内读取代码、编辑工作区、运行检查、启动本地依赖、生成文档和准备提交。
- Codex 必须在执行外部写入、生产变更、删除数据、发送对外消息、提交/推送/合并前确认授权；授权范围变化时重新确认。
- 真实密码、令牌、私钥、客户数据和生产连接串只通过受控环境注入，不进入提示词、源代码、日志、测试快照、提交或 PR 描述。
- 本地缓存、JDK、依赖下载、构建输出和运行日志不得作为产品交付物；它们必须被忽略或放在仓库外。
- 任何由 Codex 生成的测试、文档或检查只能作为证据，不能替代负责人对业务结果和风险的判断。

## 4. 资源与优先级

单人公司同时维护四条队列：

1. **用户价值**：已承诺的客户问题和可验证的产品能力。
2. **可靠性**：安全、数据完整性、可用性和阻断交付的缺陷。
3. **运营**：支持、账单、发布、备份、监控和合规证据。
4. **探索**：尚未承诺的想法、技术验证和长期重构。

默认优先级为可靠性阻断 > 已承诺用户价值 > 运营必需 > 探索。探索任务必须设置时间盒和停止条件，不得挤占已承诺交付而不更新计划。

每周只承诺有限数量的进行中任务；新任务进入时必须明确替代项。禁止以“顺手”加入未记录的需求、依赖升级或全局格式化。

## 5. 风险与授权矩阵

| 级别 | 典型变更 | 最低证据 | 人工动作 |
| --- | --- | --- | --- |
| L1 | 文档、文案、局部无行为调整 | 相关检查、差异自检 | 可自行合并到短期分支 |
| L2 | 普通业务、API 扩展、UI 流程、非敏感配置 | 测试、联调、回滚说明、PR 记录 | 负责人审阅后合并 |
| L3 | 认证授权、秘密处理、数据库迁移、生产配置、破坏性 API、依赖大升级 | 威胁/数据评审、前向或回滚方案、观察指标、完整门禁 | 明确批准；优先安排独立复核或延迟发布 |

L3 变更不能因为规模小而降级。无法获得独立复核时，必须记录例外、理由、期限和补审计划。

## 6. 经营与数据最小闭环

- 客户数据按“收集目的、保留期限、访问角色、删除/导出路径”登记；不为未来可能性提前收集。
- 生产数据至少有可验证的备份和恢复步骤；只配置备份而不演练不算完成。
- 每次发布保留版本、Git SHA、配置来源、迁移记录、健康检查和回滚结果。
- 支持反馈必须关联版本和复现证据；涉及个人数据时先脱敏再进入任务系统。
- 对外承诺、价格、SLA、退款和法律/合规判断由负责人确认并留痕，Codex 只生成草稿。

## 7. 例外与复盘

例外记录至少包含：适用任务、跳过的规则、原因、风险、批准人、补救动作和失效日期。紧急修复可以先止损，但必须在恢复后补齐测试、审查、发布证据和复盘。

每月检查一次未关闭例外、秘密轮换、备份恢复证据、过期依赖、未清理 feature flag 和长期进行中任务；每季度根据实际事故和交付数据调整契约，而不是凭感觉增加流程。
