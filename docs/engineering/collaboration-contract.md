# OPC 团队协作契约

## 1. 单一事实来源

- Issue/任务描述记录目标、范围和验收标准；PR 记录实现、风险与验证证据。
- 代码、自动化测试和纳管配置优先于聊天记录；改变决策时必须同步到任务或文档。
- `main` 始终保持可构建、可部署；任何人不得以“稍后补”为由合入已知失败。

## 2. 开发就绪定义（Definition of Ready）

开始编码前至少明确：问题或业务价值、包含和不包含的范围、可观察的验收标准、接口/数据库/权限/配置影响、依赖和负责人。缺少信息但可作低风险假设时，应在任务中显式记录；会改变业务结果或造成破坏性影响时必须先确认。

## 3. 分支、提交与变更范围

- 从最新 `main` 创建短生命周期分支，使用 `feat/`、`fix/`、`docs/`、`refactor/`、`test/` 或 `chore/` 前缀。
- 提交遵循 Conventional Commits，单个提交表达一个可解释意图，并保持可构建。
- 一个 PR 只解决一个主题；业务变更、无关重构、依赖升级和全局格式化必须拆分。
- 不得改写他人未合并提交、覆盖他人未提交工作或强推共享分支；确需历史整理时先协商。
- 生成文件、构建产物、日志、`.m2`、`.runtime` 和本地环境文件不得提交。

## 4. 风险分级与审查

| 等级 | 示例 | 最低要求 |
| --- | --- | --- |
| L1 低 | 文案、文档、局部无行为重构 | 作者自检、相关检查通过 |
| L2 中 | 普通业务、API 非破坏性扩展、UI 流程 | 至少 1 名审查者、自动化测试、联调证据 |
| L3 高 | 认证授权、数据迁移、公开 API 破坏性变化、依赖大升级、生产配置 | 领域负责人审查、回滚方案、安全/数据验证、发布观察项 |

作者负责证明变更正确，审查者负责独立挑战假设。审查优先级依次为：安全与数据完整性、业务正确性、兼容性与并发、可运维性、测试、可维护性、风格。

阻塞意见必须明确风险和建议方向；非阻塞建议标注 `nit`。作者不得仅用“本地可用”关闭可复现问题。所有阻塞讨论解决且新提交后的检查重新通过，方可合并。

## 5. PR 契约

PR 描述必须包含：

1. 背景与目标。
2. 行为变化和明确的非目标。
3. 风险等级及判断理由。
4. 验证命令和结果；UI 变更附关键状态截图或录屏。
5. API、数据库、环境变量、权限和兼容性影响。
6. L3 变更的发布、监控与回滚方案。

禁止通过关闭检查、降低覆盖率、扩大 lint 忽略、跳过测试或管理员直接推送来解决门禁失败。基础设施故障应保留日志并等待恢复。

## 6. 冲突、事故与例外

- 冲突由最了解目标分支语义的人协同解决，解决后必须重新验证，不接受机械选择一侧。
- 生产事故优先止损与恢复，所有临时措施必须可追踪；恢复后补齐审查、测试、根因和预防动作。
- 契约例外必须记录适用范围、理由、风险、批准人和失效条件。永久例外应转化为仓库配置或文档，不能只留在聊天中。

## 7. 完成交接

交接信息应让下一位开发者无需猜测即可继续：当前状态、已完成内容、未完成内容、关键决策、执行过的验证、已知风险、环境前置条件和下一步。不得在交接中记录真实秘密。
