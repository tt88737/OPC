# OPC 运行可靠性契约

## 1. 服务目标

每个面向用户的关键流程必须定义 SLI/SLO，而不是只监控“进程是否存活”。至少覆盖可用性、错误率、延迟和正确性。初始阈值应基于实际测量确定，并记录统计窗口、排除项和责任人。

- C 端关注登录、首页、查询和核心交易流程。
- B 端关注登录、权限加载、查询、批量操作、导入导出和任务执行。
- 服务端关注 API P50/P95/P99、5xx/业务失败率、依赖延迟和资源饱和度。
- 错误预算耗尽时暂停非必要发布，优先可靠性修复。

## 2. 可观测性

日志、指标和追踪使用同一请求/追踪标识串联。每个请求记录必要的路由、结果、耗时和追踪 ID，但不记录秘密或完整敏感载荷。

- 指标：请求量、错误率、延迟、JVM、线程池、连接池、GC、数据库、Redis、任务队列和业务关键计数。
- 日志：结构化、级别正确、可采集；异常保留根因链，避免同一错误多层重复打印。
- 追踪：跨进程和异步任务传播上下文；采样策略兼顾成本和故障诊断。
- 仪表盘和告警配置应纳管，不能只存在某位成员个人账号。

## 3. 健康探针

- 启动探针：应用完成初始化前不触发存活失败。
- 存活探针：只判断进程是否需要重启，不把短暂数据库抖动当作死亡。
- 就绪探针：判断实例是否可以接流，可包含关键依赖但要防止依赖故障引发全量摘除。
- 健康响应不得泄露版本漏洞、连接串、凭据、主机路径或详细组件信息给公网。

## 4. 告警契约

告警必须可行动，包含影响、严重级别、仪表盘、运行手册和责任团队。按用户影响分级：

| 级别 | 示例 | 响应 |
| --- | --- | --- |
| P0 | 大面积不可用、数据破坏、密钥泄露 | 立即响应、止损、统一指挥 |
| P1 | 核心流程严重降级、持续高错误率 | 值班快速响应，准备回滚 |
| P2 | 非核心功能异常、容量趋势风险 | 工作时段处理并跟踪 |
| P3 | 优化和低风险异常 | 纳入迭代 |

禁止对无用户影响的瞬时波动频繁呼叫；重复噪声告警必须调整。任何告警不得把秘密放进消息。

## 5. 容量与性能

- 上线前为 Web 线程、数据库连接、Redis 连接、任务线程和外部调用建立统一预算，避免各池独立放大压垮下游。
- 定义请求体、上传、导出、分页和并发上限；超限明确拒绝，不允许无限排队。
- 核心流程发布前进行基准或负载验证，记录数据规模、并发、硬件和结果。
- 容量评审关注峰值、增长率、磁盘、备份窗口和第三方配额，并保留安全余量。

## 6. 韧性与故障处理

- 所有远程调用设置连接和读取超时；重试采用退避、抖动和次数上限，仅用于可安全重试的错误。
- 关键写操作具备幂等和去重；定时任务在多实例下有明确的单执行或分片策略。
- 外部依赖故障时定义降级结果，禁止无限等待和级联重试。
- 故障注入、依赖断开、磁盘满、Redis 丢失、数据库只读等场景应在非生产环境演练。

## 7. 备份、恢复与灾备

- 为每类数据定义 RPO、RTO、备份频率、保留期、加密、异地策略和恢复责任人。
- 定期执行真实恢复演练并校验业务数据，不以备份任务“成功”代替恢复能力。
- Redis 若仅为缓存，恢复策略应允许从事实来源重建；若承载会话/队列，必须单独定义丢失影响。
- 灾难恢复手册包含流量切换、DNS、秘密、数据库、对象存储、第三方依赖和回切步骤。

## 8. 事件与复盘

事件处理中先恢复用户价值并保护数据，再定位根因。保留不含秘密的时间线、决策和证据。P0/P1 必须复盘，输出根因、促成因素、检测缺口和有负责人/截止时间的行动项；复盘不归咎个人。

## 9. 运行就绪评审

新模块或关键流程上线前必须确认：所有者和值班、SLO、仪表盘、告警、运行手册、容量、依赖清单、降级、备份恢复、安全、发布和回滚。任何一项缺失都必须显式接受风险并限定补齐期限。
