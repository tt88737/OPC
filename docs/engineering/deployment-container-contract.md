# OPC 部署与容器契约

## 1. 当前状态与目标

当前仓库交付可执行 JAR 和前端静态资源，尚无 Dockerfile、Compose 或 Kubernetes 清单。本契约定义引入容器交付时必须满足的条件；在对应文件和 CI 门禁落地前，不得宣称“支持生产 Docker 部署”。

## 2. 构建产物

- 同一提交只构建一次，经过验证的不可变产物按环境晋级，禁止每个环境重新编译。
- 产物记录版本、Git SHA、构建时间、工具链版本和 SHA-256；版本信息可从运行实例查询。
- 前后端产物分离。前端环境差异优先通过运行时配置或明确构建矩阵处理，不将秘密打入 JS。
- 依赖和基础镜像固定可追踪版本；发布产物生成 SBOM，并接受漏洞和许可证扫描。

## 3. Dockerfile 契约

- 使用多阶段构建；构建阶段与运行阶段分离，最终镜像不包含 Maven、npm 缓存、源码、测试数据或密钥。
- 基础镜像固定到明确版本，生产发布宜固定 digest；使用受维护的 Java 21 JRE/运行时。
- 容器以非 root、只读根文件系统和最小 Linux capabilities 运行；临时目录和日志目录显式挂载。
- 使用 `.dockerignore` 排除 `.git`、`.m2`、`node_modules`、日志、本地环境文件和构建缓存。
- 不在 `ARG`、`ENV`、镜像层、标签或启动命令中保存秘密。
- 定义健康检查，但探针不得依赖外部系统到导致级联重启；启动、存活和就绪语义分离。
- 进程接收并正确处理终止信号，在编排平台宽限期内停止接流、完成或中止任务并退出。

## 4. Compose 本地环境

未来 `compose.yaml` 只用于可重复的本地/集成环境，至少可编排 MySQL、Redis、后端和前端。必须具备：

- 独立网络和命名卷，不使用 host 网络作为默认方案。
- 健康检查和依赖就绪条件，不用固定 sleep 假装服务可用。
- `.env.example` 只包含占位值；真实 `.env` 被 Git 忽略。
- 数据初始化幂等，卷删除属于显式破坏性操作，文档必须警告数据后果。
- 默认端口只绑定回环地址；数据库、Redis 和管理端点不直接暴露公网。

## 5. 生产运行配置

- 配置与镜像分离，秘密由秘密管理服务以文件或受控环境注入并支持轮换。
- 明确 CPU/内存 request 与 limit、JVM 容器感知参数、临时磁盘、连接池和线程池预算。
- 应用日志写 stdout/stderr 或受控卷，由平台采集；容器内不无限滚动日志。
- 上传文件、报表和其他持久数据使用对象存储或持久卷，不写入容器临时层。
- 数据库迁移作为受控发布步骤执行，不由每个应用副本并发自动执行。

## 6. 网络与入口

- 外部流量经 TLS 入口/反向代理，配置安全响应头、请求大小、超时和限流。
- C 端、B 端、API 和运维端点按域名或路径隔离；运维端点仅对受信网络开放。
- 应用信任代理头前必须限制可信代理；客户端 IP、协议和 Host 不得无条件信任外部头。
- 数据库和 Redis 仅允许应用网络访问，生产不得使用默认密码或匿名访问。

## 7. 发布策略

- 环境按 dev/test/staging/prod 晋级；staging 应尽量复制生产拓扑和安全边界。
- 默认滚动发布；高风险变更使用蓝绿或金丝雀，并预先定义指标、观察窗口和自动/人工回滚阈值。
- 应用必须支持新旧版本短期并存，尤其是数据库结构、缓存和消息格式。
- 回滚恢复“镜像 + 配置 + 兼容数据库状态”的一致单元，不能只换回 JAR。
- 每次发布保留审批、产物摘要、迁移记录、健康检查和回滚证据。

## 8. 容器交付验收

正式声称支持 Docker 前，至少具备：后端和前端 Dockerfile、`.dockerignore`、本地 Compose、镜像扫描、SBOM、非 root 验证、健康/停止验证、持久化验证、从零启动文档以及 CI 镜像构建门禁。
