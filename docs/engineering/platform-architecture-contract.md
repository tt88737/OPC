# OPC 平台架构契约

## 1. 平台边界

OPC 按“体验端、应用服务、领域模块、基础设施”治理。C 端和 B 端可以共享设计系统、API 客户端和基础工具，但不得共享页面路由、权限假设或发布节奏。服务端当前采用模块化单体，除非有量化证据，不因团队偏好拆成微服务。

```text
C 端应用        B 端管理应用
    |                 |
    +---- HTTPS API --+
              |
         opc-admin 接入层
              |
   领域服务 / 权限 / 任务 / 生成器
              |
       MySQL / Redis / 外部服务
```

## 2. C 端契约

C 端面向最终用户，优先保证可用性、性能、隐私、无障碍和多终端体验。

- C 端拥有独立入口、路由、认证会话、错误页、埋点策略和构建产物。
- 不暴露后台菜单、内部枚举、管理接口、Druid、Swagger 或运维信息。
- 默认最小采集；Cookie、设备标识、埋点和第三方 SDK 必须经过隐私与安全审查。
- 关键路径定义性能预算，至少关注 LCP、INP、CLS、首屏资源体积和 API P95。
- 登录、注册、找回、支付或其他敏感流程必须有防重放、限流、风控和审计策略。
- C 端故障不能通过放宽服务端权限或暴露 B 端能力临时解决。

## 3. B 端契约

B 端面向运营、管理员和内部人员，优先保证权限正确、批量操作安全、审计完整和高效率。

- 当前 `frontend/` 定位为 B 端；未来 C 端不得直接塞入其 `views` 和路由树。
- 菜单可见性不等于授权；服务端必须同时校验功能权限和数据范围。
- 删除、批量修改、导入导出、权限调整等高风险操作必须确认、可追踪并提供结果明细。
- 管理员不得查看不必要的秘密、完整凭据或超出职责的个人数据。
- 长任务使用异步任务模型，提供状态、进度、失败原因、取消或重试策略，不能依赖浏览器长连接硬等。

## 4. 前端仓库布局

在只有 B 端时保持现有 `frontend/`，不为未来假设提前迁移。出现独立 C 端后，采用以下之一并由架构决策记录（ADR）确认：

```text
apps/customer-web      # C 端
apps/admin-web         # B 端
packages/ui            # 无业务权限假设的设计系统
packages/api-client    # 按公开契约生成或维护的客户端
packages/tooling       # lint、构建等共享配置
```

共享包必须有明确版本和依赖方向。C/B 端不得通过复制源码共享；设计系统不得包含具体业务 API 调用。

## 5. 服务端分层

- 接入层：HTTP 协议、认证入口、参数校验、限流与响应映射。
- 应用层：用例编排、事务边界和权限上下文。
- 领域层：业务规则、状态变化和领域事件，不依赖 Web 表达。
- 基础设施层：数据库、缓存、消息、文件和第三方集成。

当前模块映射以 `AGENTS.md` 和代码规范契约为准。新业务优先按领域形成包边界，而不是按 Controller/Service/Mapper 横向堆叠整个系统。模块之间不得直接读写对方数据表；通过服务接口或明确事件协作。

## 6. 模块与服务拆分触发条件

只有满足至少一项并有数据支持时才评估独立服务：独立伸缩需求明显；故障隔离有实际价值；安全/合规边界不同；发布节奏长期冲突；数据和团队所有权稳定独立。拆分前必须定义 API、数据所有权、失败语义、可观测性、部署和回滚成本。

不得仅因代码量、技术潮流或“未来可能需要”拆分。共享数据库、分布式事务和同步调用链增长但没有隔离收益的拆分不予接受。

## 7. 横切能力

认证授权、租户、审计、幂等、限流、缓存、文件、通知、任务和错误码必须由平台统一约定，不允许各模块自行发明不兼容实现。

- 若引入多租户，租户身份必须来自可信认证上下文，所有查询、缓存键、任务和导出均包含租户隔离；不得接受客户端任意指定租户。
- 缓存只做性能优化，不作为不可恢复的唯一事实来源；必须定义键空间、TTL、失效和穿透策略。
- 外部服务集成必须有超时、重试上限、熔断/降级、幂等和审计；重试不得放大非幂等写操作。

## 8. 架构决策记录

以下变化必须新增 ADR：引入 C 端或多应用工作区、拆分服务、引入消息中间件、变更认证模型、多租户、数据库类型变化、公共 API 破坏性升级、容器编排平台变化。ADR 至少记录背景、选择、备选、后果、迁移和退出策略。
