# 工程治理底座设计

## 目标

为 OPC 的 `main` 底座建立可执行、可重复、可审计的工程治理规则。第一阶段只处理分支门禁、工具链一致性、代码质量检查、测试覆盖率和维护文档，不改变业务行为、数据库结构或 API 业务语义。

## 范围

### 1. 分支与 CI 门禁

- `main` 作为唯一底座分支。
- GitHub `main` 启用 Pull Request、CI 必须通过、至少一名审核者、禁止强制推送和删除分支。
- CI 使用 Java 21、Node 24，并继续调用 `bin/verify-foundation.ps1`。
- 本地验证入口与 CI 使用同一套命令，失败立即返回非零状态。

### 2. 工具链一致性

- 提供 Maven Wrapper，固定 Maven 主版本，避免依赖开发者本机 PATH。
- 在仓库文档中固定 Java 21、Node 24、npm 和 Maven 的最低版本。
- 前端继续使用 `package-lock.json` 和 `npm ci`。
- 不提交本地密钥、构建输出和依赖缓存。

### 3. 代码质量门禁

- Java 引入格式检查和静态分析，先采用不改变业务代码的基线规则。
- 前端引入 ESLint/Prettier 检查；现有生成器中的长行和必要例外使用局部规则或配置说明处理。
- CI 在测试前执行质量检查，质量检查失败时不得继续发布构建产物。
- 规则必须可在本地通过统一入口执行。

### 4. 测试与覆盖率

- Maven 测试继续覆盖所有模块，并增加 JaCoCo 报告。
- 第一阶段只设置可落地的整体覆盖率下限，避免用过高门槛阻断现有底座。
- 前端保留 Node 原生测试，并将测试命令纳入统一验证入口。
- 覆盖率报告作为 CI artifact 保存；门禁失败必须给出明确模块和指标。

### 5. 维护规范文档

- 新增 `CONTRIBUTING.md`，说明分支、提交、测试、代码质量和 PR 要求。
- 新增发布/回滚说明，明确版本、构建产物、配置和数据库变更的检查顺序。
- 更新 README 的验证命令，删除与当前 Java 21/Node 24 不一致的说明。
- 维护 `task_plan.md`、`progress.md` 和 `findings.md`，使其反映真实阶段，不作为运行时配置。

## 非目标

- 不在本阶段引入 Flyway/Liquibase。
- 不修改现有业务接口、权限模型、数据库表结构或前端交互。
- 不把历史代码一次性大规模重构为新风格；质量规则先以可迁移、可解释为原则。

## 验收标准

1. 新克隆环境使用文档指定的工具链可以执行统一验证入口。
2. `main` 的保护规则已配置，直接 push 和未通过 CI 的 PR 不能合并。
3. Java 质量检查、前端质量检查、Maven 测试、前端测试和覆盖率检查均由 CI 执行。
4. 本地统一验证和 CI 使用同一组核心命令，结果可复现。
5. 规范文档包含新贡献者所需的完整命令、分支规则和失败处理方式。
6. 现有后端测试、前端测试、生产构建和安全校验继续通过。

## 风险与取舍

- 质量工具首次接入可能暴露历史代码问题，因此先采用报告基线和最小门槛，避免一次性阻断全部开发。
- 覆盖率阈值应以当前真实基线为依据；先测量再设置，不凭空设定高比例。
- 分支保护属于 GitHub 仓库设置，不完全由代码提交表达，必须在远端配置后再用 API 验证。
