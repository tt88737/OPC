# OPC 平台治理落地路线图

本路线图把契约转化为可验证能力。优先级基于“先保护数据与交付，再扩展平台形态”，不代表必须一次完成。

## P0：形成可重复交付

- 清理并阻止 `.m2`、`.runtime`、日志和本地环境文件进入版本控制。
- 为统一验证补齐可复现 Node/npm 运行时，保证本地与 CI 使用同一工具链。
- 建立后端与前端 Dockerfile、`.dockerignore` 和本地 `compose.yaml`，覆盖 MySQL、Redis、后端、B 端。
- CI 构建镜像并执行非 root、健康检查、启动/停止、漏洞扫描和 SBOM 验证。
- 引入数据库迁移框架或等价的严格版本化执行器，禁止未纳管生产 SQL。
- 定义 dev/test/staging/prod 的配置矩阵、秘密来源和环境晋级规则。
- 为登录、权限和核心只读流程建立部署后冒烟测试。

## P1：建立平台运行能力

- 定义首批 SLI/SLO、仪表盘和 P0-P3 告警，统一请求/追踪 ID。
- 建立数据库备份恢复演练、RPO/RTO 和灾难恢复手册。
- 对线程池、数据库池、Redis 池、上传、导出和分页设置容量边界。
- 建立 API 错误码、幂等键、版本/弃用和契约测试规范。
- 增加 CODEOWNERS 或等价所有权规则，标明安全、数据、基础设施和各领域负责人。
- 为认证、授权、文件上传、导入导出和管理员操作建立威胁模型。
- 把发布产物摘要、版本、Git SHA 和变更说明纳入自动发布证据。

## P2：支持 C/B 双端演进

- 在真实 C 端需求出现后通过 ADR 决定 monorepo `apps/`/`packages/` 或独立仓库，不提前搬迁。
- 建立共享设计令牌、无业务耦合组件库和分端 API 客户端。
- 为 C 端建立性能预算、SEO/无障碍（适用时）、隐私同意和第三方 SDK 清单。
- 为 B 端建立高风险操作二次确认、审批（适用时）、任务中心和完整审计。
- 定义 feature flag 生命周期：所有者、默认值、灰度范围、指标、到期和清理时间。
- 评估国际化、时区、地区格式和多组织/多租户需求，未经业务确认不提前复杂化。

## P3：按证据扩展架构

- 基于容量、故障域、合规或团队所有权证据评估服务拆分。
- 引入消息系统前明确投递语义、幂等、死信、顺序和重放策略。
- 对关键流程进行负载、故障注入、依赖降级和灾备切换演练。
- 定期清理 lint 例外、弃用 API、过期 feature flag、无所有者模块和未关闭复盘行动项。

## 每项建设的完成定义

治理能力只有在以下内容同时存在时才算完成：纳管配置或代码、自动化验证、操作文档、明确所有者、失败处理/回滚、至少一次成功演练证据。仅新增一份文档或只在某台开发机运行成功不视为完成。
