# 发布与回滚手册

本文定义人工发布的最低控制要求。仓库当前不假定已引入任何数据库迁移框架；数据库脚本必须按实际部署环境审查和执行。

## 版本与发布准备

1. 采用语义化版本（SemVer）`MAJOR.MINOR.PATCH`，发布 tag 使用 `vMAJOR.MINOR.PATCH`。tag 必须指向已通过审查并合入 `main` 的提交，禁止移动或复用已发布 tag。
2. 确认工作区干净，记录提交 SHA、版本号、审批人和变更说明。在仓库根目录使用 Java 21、Node.js 24.15.0、Maven Wrapper 和锁文件依赖。
3. 执行统一验证：

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\bin\verify-foundation.ps1
   ```

4. 如需单独复核后端发布包，在 Windows 上执行 `mvnw.cmd clean verify`；其他平台执行 `./mvnw clean verify`。前端依赖使用 `npm ci`，不得用未锁定安装替代。
5. 保存构建产物及其 SHA-256 校验记录，至少包括 `opc-admin/target/opc-admin.jar`、前端 `frontend/dist/` 归档、提交 SHA、构建时间和构建环境版本。部署前再次计算校验值并与记录比对。

## 上线前检查

1. 完成生产配置检查：确认 `OPC_PROFILE=prod`，数据库、Redis、令牌密钥和 CORS 来源均来自受控秘密管理，且 Swagger/OpenAPI、Druid Web 控制台和 DevTools 保持关闭。不得将真实配置值写入发布记录。
2. 使用最小权限的运行账户和数据库账户，确认日志、备份、监控和告警可用。
3. 数据库变更前必须完成可恢复备份，并由执行人验证备份文件可读、恢复步骤可执行、恢复时点明确。记录备份标识和保留位置，但不记录凭据。
4. 审查数据库脚本的兼容性、锁表风险、预计耗时及回滚方式。不可逆迁移必须拆成向后兼容的多阶段变更，先扩展、再切换、最后在独立发布中清理；无法证明可恢复时不得上线。

## 部署与健康检查

按“数据库兼容性变更（如有）→ 应用后端 → 前端静态资源”的顺序部署。每一步失败都停止后续步骤。

部署后的健康检查按以下顺序执行：

1. 进程与端口正常，应用启动日志无致命错误；
2. 数据库和 Redis 连接正常；
3. 后端健康端点或等效探针正常；
4. 使用非特权测试账号完成登录、权限校验和一个只读核心流程；
5. 前端资源可加载且关键 API 无异常；
6. 观察错误率、延迟、资源使用和告警，在规定观察窗口内保持稳定。

## 回滚

触发条件包括健康检查失败、错误率或延迟越过发布阈值、安全边界失效、数据校验异常。回滚负责人应立即停止流量扩展并记录开始时间。

回滚顺序为应用 → 配置 → 数据库：先恢复上一版本应用产物并核对 SHA-256，再恢复上一版受控配置；只有在应用和配置回滚不能恢复服务，且已确认数据影响后，才按演练过的恢复步骤回滚数据库。完成后重新执行全部健康检查。

对不可逆迁移不得直接执行破坏性反向脚本。应停止发布，隔离写流量，保留现场，由数据库负责人根据已验证备份决定时间点恢复或前向修复；恢复前必须评估备份之后的数据丢失，并取得业务和安全负责人批准。

## 证据与审计

无论成功或失败，都应保留版本/tag、提交 SHA、审批记录、统一验证输出、产物校验值、生产配置检查清单、数据库备份标识、部署时间线和健康检查结果。失败证据与审计记录还应包含原始错误、指标或日志片段、回滚决定、执行人、各步骤时间及最终验证结果；记录中不得包含秘密值或个人敏感信息。
